# SIH Judge Q&A Guide

**1. What problem are you solving?**
We are solving the subjectivity and lack of digital chain-of-custody in colorimetric field drug testing.

**2. Are you replacing the existing drug-testing kit?**
No. FieldSure is a digital companion that augments the existing chemical test with an objective, verifiable digital record.

**3. How does the reference card help?**
It provides known baseline colors (white, black, gray, pure RGB) allowing the CV pipeline to mathematically correct for variations in ambient lighting and camera sensors.

**4. How is image lighting handled?**
If lighting is too dark or too bright, the `ImageQualityValidator` immediately rejects the image before processing. Otherwise, the reference card enables perspective and color-space calibration.

**5. How does classification work?**
Once calibrated, the specific region of interest (the chemical reaction) is extracted. Color features are evaluated against kit-specific configured thresholds. 

**6. Why use a kit-specific configuration?**
Chemical reagents react differently (e.g., Marquis turns purple for opiates, Cobalt turns blue for cocaine). A universal model is scientifically invalid.

**7. What happens when the image is ambiguous?**
The pipeline intentionally fails safely by returning an `INCONCLUSIVE` result. We do not force a binary guess.

**8. How do you prevent tampering?**
The Flutter app never dictates the final outcome. The backend calculates a cryptographic hash chain including the image hash, metadata, and results, which is then signed by a private key residing securely on the server.

**9. Why use SHA-256?**
It provides an irreversible, highly collision-resistant fingerprint of the captured image, ensuring any modification of the photo breaks the hash.

**10. Why use digital signatures?**
It mathematically guarantees that the backend authority created the record and that it has not been altered at rest or in transit.

**11. Can an officer modify the result?**
No. The backend is authoritative. The client UI is merely a terminal viewing the server's cryptographic truth.

**12. How is GPS obtained?**
Via the mobile device's secure location services at the exact moment of capture.

**13. How is timestamp authority handled?**
The device records a `clientCreatedAt` timestamp, but the final, authoritative `serverCreatedAt` and `signedAt` timestamps are generated by the NestJS backend to prevent device clock manipulation.

**14. What happens offline?**
The app writes the captured test to a local SQLite database (`drift`). The test is marked `PENDING_SYNC`.

**15. How is duplicate synchronization prevented?**
The mobile client generates a UUID (`testId`) upon creation. The backend uses this as an idempotency key, so if a sync request is sent twice due to network drops, the database safely ignores the duplicate.

**16. Where are images stored?**
Raw images are intended for an S3-compatible Object Storage layer (like MinIO or AWS S3), while the image hashes are stored in the relational database.

**17. Why PostgreSQL?**
It provides ACID compliance, strong relational integrity for chain-of-custody, and robust JSONB support for dynamic ML features and diagnostics.

**18. Why Flutter?**
Flutter provides native performance, a unified UI layer, and access to low-level camera/hardware APIs across both iOS and Android from a single codebase.

**19. Why NestJS?**
It forces strict architectural patterns (Guards, Interceptors, DTO validation) which is critical for maintaining a highly secure, enterprise-grade chain of custody.

**20. Why Python/OpenCV?**
Python is the industry standard for CV/ML pipelines, offering unmatched support for matrix operations (NumPy) and computer vision algorithms (OpenCV).

**21. Is the ML model scientifically validated?**
**No.** We are currently using a demonstration configuration pipeline (`DEMO-CONFIG-v1`). 

**22. What data is required for validation?**
Thousands of labeled, real-world field-test images captured under varying conditions, explicitly correlated with GC/MS laboratory confirmations.

**23. How would this scale to multiple kits?**
Because the pipeline is driven by a `configurationVersion`, expanding to a new kit merely requires defining a new JSON configuration representing the geometric boundaries and color profiles of the new test, without rewriting the core application.
